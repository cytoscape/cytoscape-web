branch·review / merge planning

Which branches conflict, which touch the same code, and what order to merge.

Overview

Recommended merge order

Land the independent tier first (clean into base, no peer conflicts — safe in any order or in parallel), then work the sequenced tiers, resolving each branch against the peers listed. This is a greedy heuristic, not a proven-optimal schedule — re-run after each merge.

Conflict matrix

Ground truth from an in-memory git merge-tree of each branch pair. The leading base column is each branch merged into the base. Hover a cell to see conflicting files.

clean merge substantive conflict trivial only (lockfile/.gitignore/CHANGELOG) error / no merge base

File-overlap heatmap

Jaccard similarity of each pair's changed-file sets — a heuristic for "touch the same code". Darker = more shared files. Overlap is a prompt to look; the conflict matrix above is the ground truth.

Branches

Per-branch review sizing. Click a column to sort. Oversized branches (churn over the threshold) are harder to review well and good candidates to split.
